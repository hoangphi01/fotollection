# Optimization — Fotollection

> **Status:** Draft v0.1 · **Last reviewed:** 2026-11-16
>
> Performance is the #1 product quality for Fotollection, which targets enthusiast and professional photographers.
> This document holds the **budgets**, the **methodology** used to measure them, the **design techniques** that meet them, and a **log** of every measurement.
> The budgets themselves are defined as NFRs in [PRD.md](PRD.md#7-non-functional-requirements). This file explains how we hit and verify them.

## 1. Rules

1. **Measure first.** No optimization is merged without a before/after benchmark logged in [§5](#5-benchmark-log).
2. **Budgets are tests.** Once code exists, CI compares benchmark results against `bench/budgets.toml` and fails if a regression exceeds 10%.
3. **Optimize the pipeline, not the micro-op.** Throughput comes from parallelism, avoiding redundant decodes, and bounded memory, rather than from clever loops.
4. **Never trade correctness for speed.** Orientation, ICC profiles and stamp placement must be identical between the fast path and the slow path.
5. **Speed is the first quality of a photo tool that works in batches.** Every change that renders many photos at once (a grid, a sheet list, an export) is measured on a full screen of them, in the build the owner uses, before it ships; a change of setting must answer at once, and anything that can take more than 200 ms shows that it is working. Perceived speed counts as much: while a new answer loads, the last one stays on screen, so typing or a switch never makes the panel blink or jump (STYLE_RULE §4, "Nothing blinks, nothing jumps").
6. **An optimization is an experiment** (owner, 2026-11-15). It starts from a hypothesis that names the stage and the expected gain; the baseline is measured on the same build, files and machine, the machine quiet (`scripts/resources.sh`: load below half the cores, no VM or build beside it); one change at a time, the median of at least five runs with their spread; a change is kept only if its gain is larger than that spread, and the §5 row records the machine's state with the numbers. A run on a busy machine is not a measurement: on 2026-11-13 a Docker VM on two cores made `measure_look` read 59–63 ms for the 38 ms the same code had measured the day before.

7. **We measure to guard the app, not to polish a number** (owner, 2026-11-21). Every number is relative: the same phone measures differently new and after a month, and so does this laptop. A measurement exists to prove that a change made the app faster, or that dozens of updates did not make it slower (the monthly run against the budgets). So: a release is not held to measure again a number already measured; a number is measured again only when its code changed or a regression is suspected; a difference within a few milliseconds or a few per cent between two runs is not a finding to chase. **The website and the README tell a story from the results already in `bench/results/`**, as Apple does: "up to 20× faster", "under the budget", "a thousand photos in a blink", a rounded number with a comparison, never a decimal to defend; the exact value, its date and machine stay in the chart's footer, `bench/results/` and the Wiki's table. Where two pages show different values of one measure (two dates, two methods), the page shows one and the other goes to the fold or the Wiki, rather than measuring both again.

## 2. Why native Rust instead of a web app

*Vite is only a build tool. The real comparison is between the browser runtime (JS + Canvas/WASM) and native Rust code.*

### 2.1 Measured: the same job in Chromium

`bench/run.sh <photo-folder>` runs both sides on the same folder. The browser side (`bench/web/`) does the export job in headless Chromium:

1. `fetch`, then `createImageBitmap` with EXIF orientation.
2. Centre crop to 2:3.
3. Date stamp with `fillText`.
4. `OffscreenCanvas.convertToBlob` as JPEG q0.95.

The browser runs one Web Worker per logical core. For previews, it decodes once, caches a 2048 px bitmap (like T2), then re-renders 1600 px 20 times. The Rust side is `measure_folder --json`. Peak RSS comes from `/usr/bin/time -l` for Rust, and from the sampled RSS of the browser's process tree for Chromium. Each metric is the median of 3 runs. Raw numbers are in `bench/results/`, and the chart is `docs/images/bench.svg`.

Latest result on REF-MAC (M3, 8 cores), 95 × 16 MP JPEG, 2026-10-23, after a cool-down (charts and the full table: [RESULT.md](RESULT.md)):

| Metric | Fotollection (Rust) | Chromium 156 | |
|--------|--------------------:|-------------:|---|
| Batch export | 18.0 photos/s (6 in flight) | 17.9 photos/s (8 workers) | Tie |
| Warm preview, 1600 px, p50 | 17.4 ms (26.0 ms before the screen encoder) | 18.5 ms | Rust faster |
| Cold preview (first open) | 120 ms | 119 ms | Tie |
| Peak memory | 1.35 GB | 1.78 GB | Rust 24% lower |

The work is not identical, and the differences favour the browser:

- Chromium always encodes 4:2:0 (verified from the SOF0 marker). The API cannot request 4:4:4. Fotollection encodes 4:4:4, so it writes twice the chroma data.
- The browser discards its blobs. Fotollection writes every file to disk atomically, with no EXIF, so GPS is always stripped.
- Fotollection's RSS covers the whole `measure_folder` run, including T1 thumbnails for all 95 photos, not only export and preview.

**What this changes.** The earlier hypothesis, that `canvas.toBlob` is slow, is **wrong**. Chromium's libjpeg-turbo with SIMD matches our pure-Rust codecs on throughput, and it beats our preview path. Native still wins on what the table below lists: encoder control, bounded memory, colour, bit depth, formats and file output. Raw speed is not the argument for native.

Follow-ups, measured in Stage 1 with `measure_folder` (median of 20 warm renders, 3 runs):

| Warm preview step (1600 px, from the cached 2048 px T2) | Time | Share |
|----------------------------------------------------------|-----:|------:|
| Crop + Lanczos resize (`fast_image_resize`) | 9.7 ms | 37 % |
| Date stamp (`ab_glyph`; `skrifa` since FR-134, §5) | ≈ 0.1 ms | ≈ 0 % |
| JPEG encode q85, 4:4:4, optimized Huffman (`jpeg-encoder`) | 16.2 ms | 62 % |

- **Preview latency (done in Stage 2).** The encoder was the bottleneck. Previews and thumbnails now use `EncodeOptions::screen` (plain Huffman tables, 4:2:0), exports keep `EncodeOptions::print` (4:4:4; optimized tables until 2026-11-04, the standard ones since, §5). Encode went from 16.2 to 11.7 ms without the Huffman pass and to 7.0 ms with 4:2:0; the warm preview from 26.0 to 17.4 ms, below Chromium (18.5 ms). A CatmullRom resize filter was slower than Lanczos3 (12.5 vs 9.7 ms) and was not kept. `turbojpeg` is no longer needed for previews.
- **Export concurrency: keep 6 in flight.** 8 in flight is 8–13 % faster (latest medians 19.5 vs 18.0 photos/s), but peak RSS rises from 1.30–1.41 GB to 1.70–1.77 GB on 16 MP photos. Scaled to 24 MP buffers, that would break the 2 GB budget ([NFR-004](PRD.md#nfr-004--memory-ceiling)), so `default_inflight()` stays at 6. **Measured again 2026-11-05** ([ADR-0039](adr/0039-gpu-for-editing-cpu-for-exports.md), `bench/results/inflight.json`): a photo is decoded and encoded on one core, so throughput follows the photos in flight; on 26 MP JPEGs 4.9, 9.4, 11.5, 12.5 photos/s at 2, 4, 6, 8, but on the Prague trip with its RAW files 9.54 at 6 and 9.2–9.3 at 8 with 0.2 GB more. The memory budget had held 26 MP photos to 4: `EXPORT_MEMORY_BUDGET` is now 1.6 GB (the estimate is about twice what a photo holds), the cap stays at 6: 26 MP JPEGs export at 10.8 photos/s instead of 8.9 (+21 %), peak 1.08 GB.

### 2.2 Qualitative comparison

| Concern | Web (browser) | Native Rust (Tauri) |
|---------|---------------|---------------------|
| JPEG decode | Fast: browsers use libjpeg-turbo internally | Same or faster, plus **DCT-domain downscaling** (1/2, 1/4, 1/8) for thumbnails |
| Parallelism | Web Workers. Buffers are copied or transferred | `rayon` on all cores, shared memory with zero copies |
| JPEG encode | `convertToBlob`: fast (§2.1), but quality is the only control; always 4:2:0 | `jpeg-encoder` with full control (quality, 4:4:4) |
| Memory ceiling | About 2–4 GB per tab, so large batches crash | System RAM, explicitly bounded by back-pressure |
| Colour management | Canvas usually converts to sRGB and drops the ICC profile | ICC preserved or converted exactly (`qcms`) |
| Bit depth | 8-bit | 16-bit capable, needed for RAW in Phase 3 |
| HEIC | Not supported in Chrome or Firefox | The OS codecs (ImageIO, WIC; [ADR-0017](adr/0017-heic-through-os-codecs.md)) |
| File output | ZIP download, or the File System Access API (Chromium only) | Direct folder writes with atomic renames |
| **Measured: 95 × 16 MP export (§2.1)** | 18.7 photos/s at 4:2:0, blobs not written | 18.6 photos/s at 4:4:4, files written |

**Conclusion:** measurement confirms that the advantage is not raw speed. It is control over memory, encoder quality, colour correctness and file handling. For a professional photo tool, these matter most. See [ADR-0001](adr/0001-desktop-tauri-over-web.md).

## 4. Design techniques

### 4.1 Multi-tier preview

| Tier | Source | Size | Used for |
|------|--------|------|----------|
| T0 | EXIF-embedded thumbnail | ~160 px | Instant grid on first paint |
| T1 | DCT-scaled decode (1/8) | ~400 px | Sharp grid thumbnails, disk-cached plain; served through the photo's look, kept in memory (32 MB, ADR-0047) |
| T2 | Decode or RAW develop + resize to 2048 px, kept on disk as a standard preview (FR-091) | ~2 MP | Interactive preview of stamp and crop; opens any photo in ~27 ms once made |
| T3 | Full decode | Original | Export only |

The preview renders the same `RenderPlan` as the export ([ARCHITECTURE.md §4](ARCHITECTURE.md#4-processing-pipeline)), only at T2 scale.

**Photo Style cost ([FR-039](PRD.md#fr-039--photo-style-looks)):** style parameters are baked into a 33³ 3D LUT (about 430 KB, built in about 1 ms when a parameter changes) plus a 1D tone curve. Applying the look is **one tetrahedral lookup per pixel** in integers (`looks.rs`), across rayon threads. Estimated cost: about 2 ms on a 2 MP preview (within [NFR-002](PRD.md#nfr-002--preview-latency)) and about 15–25 ms per 24 MP export on 8 cores (to be checked against [NFR-003](PRD.md#nfr-003--export-throughput) in Phase 0/2 benchmarks). Grain uses a precomputed tiled noise texture with a per-photo seed, so it is deterministic and costs no extra RNG.

**Instant previews ([FR-091](PRD.md#fr-091--instant-previews-standard-previews-on-disk-and-memory-used-well), [NFR-012](PRD.md#nfr-012--culling-navigation), [ADR-0041](adr/0041-instant-previews-disk-and-memory.md)):** after the thumbnails, every photo's T2 is made in the background and kept on disk (0.66 MB a photo), so a click on any photo opens it from there (27 ms p50, against 278 ms for a JPEG and 440 ms for a RAW decoded on demand). The preview keeps up to a quarter of the machine's RAM by bytes, and loads the next two photos in the direction of travel and the one behind once the photo on screen has landed. RAW develops for work the user does not wait for (standard previews, prefetch, the export's estimate, exports, analyses) wait at the develop gate while the photo on screen needs one (`raw::with_priority`); since v0.11.1 a develop is background unless the preview marks it, a photo browsed past stops going first (`raw::show`), a prefetch is kept below the photo on screen and runs on one worker, and work no longer wanted when its develop's turn comes is dropped (ADR-0041, amended). Since v0.12.0 the user sets the memory share (15 / 25 / 40 %) and the cache limit (2 / 5 / 10 / 20 GB) in the Settings window (FR-086), or lets *Auto* choose from the machine; and when the machine runs short of memory (under a tenth available, checked every 5 s), the previews keep a tenth of their budget until memory comes back, then the user's share again (`PreviewCache::follow_memory`).

### 4.2 Avoid redundant work

- Decode each source **once** per export, and never twice to get both a thumbnail and the full image.
- Crop before any per-pixel work, so only the pixels that survive are processed.
- For **crop-only** JPEG output (no stamp), use a lossless DCT-domain crop (`tjTransform`). This is faster and gives zero quality loss.
- Memoize geocoding per ~1 km grid cell. A trip of 800 photos needs only tens of lookups.
- **Render a grid from thumbnails, never from the photos.** A tile only needs a few hundred pixels: the Collage grid's sheets come from each photo's cached T1 (400 px), kept for 64 photos, so a change of setting renders ten sheets in 29 ms instead of 4 s, when each sheet decoded its two photos again (§5, 2026-11-01). The large preview keeps the 2048 px sources.

### 4.3 Parallelism and back-pressure

- Bounded channels between decode → render → encode → write. The in-flight limit is derived from the memory budget: `max_inflight = min(num_cpus, budget / bytes_per_decoded_image)`.
- Writing to disk is I/O-bound and runs on a small dedicated pool, so it never blocks the CPU stages.
- Thumbnail work runs at low priority and pauses while an export is running.

### 4.3.1 Lesson: keep interactive work off background queues

In the first slice, protocol requests shared one pool with background T1 generation. In unoptimized dev builds, grid tiles stayed blank until all 215 thumbnails were done. The fix splits the work into interactive and background pools (ARCHITECTURE.md §5), and `fotollection-core` is built at `opt-level = 3` even in dev (DEVELOPMENT.md §4.1).

### 4.4 SIMD and codecs

- `fast_image_resize` uses NEON on Apple Silicon and AVX2 on x86-64. libjpeg-turbo is not used: JPEGs are decoded by `zune-jpeg` (`jpeg-decoder` as the reference) and encoded by `jpeg-encoder`.
- Release builds use `lto = "fat"`, `codegen-units = 1` and `panic = "unwind"` (ADR-0029): a panic must stay where it happened, never take the app down (ADR-0048), so every pool has a panic handler (`pool::contained`), image routes answer a panic with 500 and commands with an error.
- Do **not** enable `target-cpu=native` for distributed builds. Use runtime feature detection instead.

### 4.4.1 Services and what each may spend (ADR-0048)

Each service has one owner and one bound; a failure costs that service's work only.

| Service | Runs on | Bound | When it fails |
|---|---|---|---|
| Image server (`protocol.rs`) | interactive pool, 2 threads (`pool::contained`) | one request a thread; previews in memory within a quarter of RAM (§4.1) | that image answers 500 with its code |
| Thumbnails, standard previews, look thumbnails | background pool, 2 threads; one supervised thread a batch | the cache limit (`ui.cacheLimitGb`), look thumbnails 32 MB | the batch's progress ends; a miss is made again |
| Export | its own pool, `inflight_for` photos at once (NFR-004) | memory of the largest photos in flight | the job ends with an error; the dialog never stays "exporting" |
| Analysis (best shots) | background pool, one supervised thread | its cache on disk | the job ends, *Find best shots* starts afresh |
| RAW develop | its own pool, one develop at a time (`raw::DEVELOP`) | one full image | that photo's decode error |
| Autosave, memory watcher, prefetch | one supervised thread each, restarted with a back-off | — | started again after 1–60 s |
| Interface parts | webview | — | that part shows `PartFailed`; the rest goes on |

### 4.5 Deferred until measured

These ideas are recorded here and **not** implemented until a benchmark shows they are needed:

- GPU compositing or resize via `wgpu`.
- A custom JPEG encoder or decoder.
- Memory-mapped input files.
- A persistent library database.

### 5.1 Planned measurements

Recorded so they are not forgotten; each one becomes a row above once it is run.

- **Complexity at scale: the big O of every path over many photos (owner, 2026-11-12, next after v0.14.1's features).** List each path that touches N photos and write its complexity next to it, from the code, then prove it by measure: import and EXIF, the gallery's filters and sort, best-shot grouping (pairs of photos compared, or a window), place inference (FR-031), a look given to many photos (FR-114), copy and paste of settings, undo history, export, the thumbnail cache's eviction.
  1. A `measure_scale` example runs each path at 1,000, 5,000, 10,000 and 50,000 synthetic photos and prints time and peak RSS per size; a path whose time grows faster than N log N is a finding.
  2. Each finding gets its fix (an index, a sort once, a window instead of all pairs) and a row in §5 before and after; the budgets of §3 stay the bar.
  3. Rust first: the work stays in the core, parallel where no caller waits (ADR-0044), and the measure says so.
- **Why so little space is left (owner, 2026-11-12).** On REF-MAC the free disk stays near 8.5 GB and swap near full, so builds and tests wait (DOCS_GUIDE §3). Find where it goes before guessing: `target/` (13 GB of debug alone, its `incremental` and `examples`), the app's own caches (thumbnails, previews, analysis; their limits in Settings → RAM & cache), `node_modules`, the Playwright browsers, the screenshot work folders; then the app's memory under a 5,000-photo batch (RSS against the 2 GB ceiling, NFR-006). Each finding gets its cause and its fix (a smaller profile, a cache limit, `scripts/clean.sh`), and what the app itself keeps is measured, never assumed.
- **RAW to JPEG batch export vs Lightroom Classic (NFR-017, FR-016).** The Performance page compares RAW against Adobe DNG Converter only, because the one Lightroom figure found is not comparable yet. Published figure: Lightroom Classic 13.1 exported 222 Nikon Z8 RAW files (45 MP) to full-size JPEG q100 in Adobe RGB in 56 s on an M3 Max (12 performance cores, 64 GB), about 0.25 s per file; 1 min 27 s on an M2 Max, 2 min 25 s on a Ryzen 9 7945HX ([Adobe Community, 2024-02-01](https://community.adobe.com/t5/lightroom-classic-discussions/performance-lightroom-classic-with-apple-silicon-m2-max-m3-max/td-p/14394975)). Our 0.9 s median is one photo's develop, not batch throughput, and RAW develops one at a time to stay under the 2 GB ceiling. To do:
  1. A `measure_raw_export` example: the nine CC0 samples (`bench/raw-samples.json`), repeated to a batch of about 100, through the real export path (develop, crop, stamp, JPEG q95), wall time and peak RSS, on REF-MAC.
  2. Compare per megapixel and say which machine each figure comes from; add Lightroom to `bench/results/raw.json` and the RAW chart only then, even if Lightroom is faster.
  3. If the batch is far slower, measure two develops at once against the memory ceiling before changing the one-at-a-time rule.
  4. Needs a release build: free disk first (`scripts/resources.sh`, at least 10 GB).
- **Camera over USB, Step 0 (FR-062, FR-063, NFR-018, NFR-019, [ADR-0026](adr/0026-cameras-through-the-os-usb-stack.md)).** `probe_camera` on a Sony a6400 and a Panasonic GX9, by cable, macOS then Windows: declared PTP operations, capture from the computer (standard, then the maker's), whether the camera's own shutter is reported, live-view frames per second, size and latency, time from the shutter to the full file on disk for JPEG and RAW, and the cost of re-importing the session folder against importing one file. Checklist in [cameras/README.md §3](cameras/README.md#3-step-0-what-to-measure).
